# Common Mistakes Reference

Full list. See SKILL.md for the critical subset kept inline.

| Mistake | Fix |
|---|---|
| Running commands on host when Docker is present | Always check for `docker-compose.yml`, `docker-compose.yaml`, `compose.yml`, or `compose.yaml` first |
| Assuming `shopware-cli` is available | Confirm it at Step 0; install via Homebrew or the Cloudsmith apt repo if absent. mysqldump fallback covers Phase 1 only — Phase 4 still requires shopware-cli |
| Creating a new upgrade branch without checking for an existing one | Run `git branch -a \| grep <ticket>` first — a prior attempt may already have the version bump and recipes |
| Running `composer recipes:update` with uncommitted tracked files | The command needs a clean index — stash the modified tracked files (`git stash push -- path/to/file`), run the recipe, then `git stash pop` |
| Leaving `shopware.paas-meta.updates-for-deleted-files.patch` in the project root | If `.platform/applications.yaml` doesn't exist, paas-meta recipe update writes this stale patch file — delete it before committing |
| Running `shopware-cli` on host when Docker is present | `shopware-cli` is also run inside the container — same rule as every other command |
| Updating all `shopware/*` packages blindly | Only update pinned `shopware/*` packages — scan all entries, not just core/storefront/administration |
| Skipping `upgrade-check` before bumping version | Extensions may break silently without it |
| Forgetting `--no-scripts` on `composer update` | Scripts can fail mid-upgrade before build step |
| Not asking about branch naming convention | Creates branch that won't pass CI naming rules |
| Running `composer recipes:update` with `-T` | The command is interactive — requires a TTY; drop `-T` from `docker compose exec` |
| Discounting upgrade-check warnings because "it's only a patch upgrade" | upgrade-check auto-selects the **latest** release and prints `INFO Auto selected version <x>`. **Read that line and compare it to your target.** If they match — which is normal when upgrading to the newest patch — the warnings are directly relevant and must be acted on. Only discount them when the auto-selected version is a newer major/minor than your target |
| Treating "Not compatible" as a hard blocker for private plugins | upgrade-check queries the Store API — private plugins always show "Not compatible". Read the plugin's own `composer.json` |
| Forgetting to widen path-repo plugin constraints for major upgrades | All `custom/static-plugins/*/composer.json` need `shopware/core` widened — the constraint blocks resolution even with path repos |
| Running `composer recipes:update` multiple times without committing between | Each call requires a clean git index — commit after the first recipe before applying the next |
| Generating deployment checklist before smoke tests pass | Phase 14 only runs after Phase 13 confirms HTTP 200 on storefront and admin with no CRITICAL log entries |
| Writing generic QA Notes | QA Notes must name each bumped plugin, each applied recipe, and each API fix — testers need scope, not boilerplate |
| Treating HTTP 200 on /admin as a passing smoke test | The admin can return 200 while broken — visually confirm translated labels or check the page title is "Login \| Shopware Administration" |
| Tailing prod.log when APP_ENV=dev | Check `.env` for APP_ENV first — use dev.log in dev mode, prod.log in production |
| Type-hinting SalesChannelContextService (concrete) in plugin constructors | In 6.7 the Commercial/B2B packages inject a decorator that implements the interface but does not extend the concrete class — always use `SalesChannelContextServiceInterface`. PHPStan does NOT catch this — it only surfaces at runtime. Grep during Phase 9b: `grep -rn "SalesChannelContextService[^I]" custom/static-plugins/ --include="*.php" \| grep -v Parameters` |
| Diagnosing raw snippet keys as a JS bundle problem | Raw snippet keys mean the `/api/_admin/locales` JSON parse failed — curl the endpoint directly and look for HTML injected after the JSON by the Symfony dev toolbar |
| Using `{% sw_include %}` with a path that no longer exists, even inside `{% if %}` | Shopware's `sw_include` resolves template paths at compile time, not render time — a missing template inside a `{% if not feature('FLAG') %}` block still causes a `LoaderError` on first render. Remove the dead block entirely. |
| Leaving `shopware.core.updates-for-deleted-files.patch` in the project root | If `.htaccess` / `public/.htaccess.dist` don't exist, `composer recipes:update shopware/core` writes this stale patch file — delete it before committing, same as the paas-meta patch |
| Treating OOM after `cache:clear` as a real application error | First request after `cache:clear` can exhaust memory while Twig compiles all plugin templates simultaneously in the debug container. If the only CRITICAL log entry is `OutOfMemoryError` at `Template.php` and subsequent requests return 200, the smoke test passes — do not investigate further. **Distinguish from persistent OOM (next row)** |
| Plugin `sw_extends` on a removed 6.7 template path causes circular Twig loop → persistent OOM on every request | `storefront/layout/navigation/navigation.html.twig` was removed in 6.7 (moved to `storefront/layout/navbar/navbar.html.twig`). Without a core base to terminate the `sw_extends` chain, Shopware wraps remaining plugin overrides (e.g. ATFThemeWareExtension ↔ TcinnThemeWareClean) in an infinite loop. **Signature:** `OutOfMemoryError` at `Template.php` AND `Maximum call stack size reached. Infinite recursion?` on every storefront or header ESI request — not just the first post-cache-clear hit. **Fix:** Grep `grep -rn "layout/navigation/navigation.html.twig" custom/static-plugins/ --include="*.twig"`. Delete all custom overrides of this path. Migrate nav customisations to a new `storefront/layout/navbar/navbar.html.twig` that extends `@Storefront/storefront/layout/navbar/navbar.html.twig` and overrides `layout_navbar_nav_element` or `layout_navbar_menu_items`. Also remove any `sw_include` of the old navigation path from header templates — ThemeWare's `layout_header_navigation` already renders `navbar.html.twig` in 6.7. Run `bin/console cache:clear` after. |
| Custom 6.6 navigation templates extending `layout/navigation/navigation.html.twig` silently break navigation in 6.7 | Same root cause as persistent OOM row above. If no other plugin is in the extends chain the symptom is an empty nav rather than OOM. Audit during Phase 9b: `grep -rn "layout/navigation/navigation.html.twig" custom/static-plugins/ --include="*.twig"` |
| Diagnosing `shopware/paas-meta` recipe conflicts as a skip | Projects with custom `.platform/applications.yaml` and `config/services.yaml` always produce merge conflicts — use `git checkout --ours` as the base, then manually pick up new additions from the recipe diff (e.g., MESSENGER_TRANSPORT_DSN env defaults, updated NODE/shopware-cli versions) |
| Skipping Phase 11 (Flex recipes) | Always run `composer recipes | grep "update available"` after the version bump — patch upgrades can carry recipe updates for non-Shopware packages (e.g. doctrine/deprecations, squizlabs/php_codesniffer). Create a visible plan/task entry for it so it can't be silently dropped |
| Skipping Phase 15 on a "clean" upgrade | Every upgrade surfaces something — a version constraint quirk, an undocumented recipe conflict, a timing issue. If Phase 15 produces nothing, that itself is worth noting |
| Relying solely on curl for Phase 13 smoke test | curl confirms TCP connectivity and HTTP status, not render correctness. Use `/browser` to visually verify the storefront renders with the correct theme and the admin shows translated labels |
| Assuming patch upgrades don't introduce breaking constructor changes | Shopware 6.6.10.18 added `StateMachineLocker` as a 6th arg to `StateMachineRegistry::__construct()` as part of the Sync API privilege escalation security fix. Any plugin decorating `StateMachineRegistry` must inject and forward it. Symptom: storefront 500 immediately after upgrade, log shows `ArgumentCountError: Too few arguments... exactly 6 expected`. Grep: `grep -rn "StateMachineRegistry" custom/static-plugins/ --include="*.php"` |
| Using `shopware-cli version` to check the CLI version | `shopware-cli version` is not a valid subcommand — use `shopware-cli --version` instead |
| Expecting PHPUnit to survive a `composer update` when not pinned in require-dev | PHPUnit can be a transitive dep in Shopware projects. If upstream packages are reorganised during a `composer update`, `vendor/bin/phpunit` disappears silently. Pin `phpunit/phpunit` explicitly in `require-dev` |
| Assuming a `composer update` failure with `Could not authenticate against github.com` is a code/network problem | It's usually an expired/revoked GitHub PAT in `auth.json`'s `github-oauth.github.com` entry. Composer masks this for a while — it silently falls back to slow anonymous git-mirror clones per package (visible as `Failed to download ... Now trying to download from source`), then still hard-fails at 100% in `AuthHelper.php`, leaving `composer.lock` updated but `vendor/` only partially checked out. Diagnose fast: `curl -H "Authorization: token <tok>" https://api.github.com/rate_limit` → `401` confirms the token is dead. Composer auto-strips a dead token from `auth.json` on failure — a retry with no token (anonymous GitHub access) often succeeds; rotate the PAT before the next upgrade so it isn't relying on the anonymous rate limit |
| Treating a non-200 storefront root as a build failure | Some stores run a login-forcing plugin (e.g. a B2B/wholesale/dealer-only storefront) that 302-redirects `/` to `/account/login` by design. Before flagging Phase 13 as failed, check `bin/console plugin:list` for anything like a "ForceLogin" plugin and verify the redirect target itself returns 200 with real (non-raw) content |
| Assuming `vendor/shopware/*` is a dist install | If installed as git source checkouts, `composer update` aborts with `VcsDownloader ... Source directory /var/www/html/vendor/shopware/storefront has uncommitted changes`. Cause: `bin/build-administration.sh` compiles assets *into* `vendor/shopware/*/Resources/public/`, and macOS/OrbStack bind mounts flip file modes `100644→100755`. Detect at Step 0: `find vendor -maxdepth 3 -name .git`. **Fix at root cause** — `rm -rf` the affected packages then `composer install --prefer-dist`. Merely cleaning the dirty files leaves the checkout in place, so it recurs on the next upgrade after any admin build. Check `composer config preferred-install` — it is often already `dist`, meaning the source checkouts were contradicting config intent |
| Trusting `composer.lock` after a failed `composer update` | A pin on `shopware/core` governs **resolution**, not **installation**. When the install step dies partway, the lock is fully rewritten and looks perfect while `vendor/` holds a **split-version tree** (core on the new version, storefront/administration/elasticsearch stranded on the old one). Always verify on disk: `git -C vendor/shopware/<pkg> describe --tags`, or compare each package's own version against the lock. `bin/console --version` reports core's version only and will look correct |
| Using `tail` on `composer recipes` output | The list is **alphabetical**, so `tail -30` silently truncates the top and hides `shopware/administration`. Use the documented form verbatim: `composer recipes \| grep "update available"` |
| Reasoning about log timestamps without checking the container's clock | `var/log/*.log` is written in **UTC** while the host shell may be local (e.g. UTC+8), so a `07:0x` entry is `15:0x` local. An 8-hour misread **inverts causality** — pre-existing errors look upgrade-caused and vice versa. Establish the offset first: `docker compose exec <service> date -u` |
| Grepping the admin `<title>` with a line-based pattern | Shopware renders `<title>` across **three lines**, so `grep -oE '<title>[^<]*</title>'` returns nothing and reads as a failure on a perfectly healthy page. Inspect the raw head instead (`curl -s <url>/admin \| head -c 1200`), or read the browser tab title |
| Conflating "Not available in Store" with "Not compatible" | Two different verdicts. **"Not available in Store"** = the Store API lookup found nothing — normal and expected for *every* path-repo/private plugin, never a blocker. **"Not compatible"** = the plugin was found and your target exceeds its declared max — only this one can block. Both still require reading the plugin's own `composer.json` |
| Putting `--include` after `--` in a grep call | `grep -rn -- "->getDefinition()" path --include="*.php"` makes ugrep treat `--include=*.php` as a filename and warn `No such file or directory`, so the removed-API scan may not search what you think. Put flags first: `grep -rn --include="*.php" -e "->getDefinition()" path`. Sanity-check any "clean ✅" result with a pattern you know matches |
| Scoping QA from the upgrade type alone, so a `.0`→`.1` gets "patch = light regression test" | **Read the release notes before writing QA Notes.** A patch release can be a pure security release (6.7.13.1 shipped 10 CVEs across admin auth, Store API, media, Twig, App Scripts and webhooks), and a security release **inverts the risk model**: the danger is not broken code but **newly-enforced validation rejecting input that previously passed**. Nothing in the pipeline surfaces this — `upgrade-check` is green, PHPStan is clean, `plugin:list` reports `0 upgradeable`, and an importer still silently starts dropping records in production. Scope QA to **write** paths (imports, media persistence, custom-entity writes, outbound webhooks), not read paths |
| Cross-referencing the security changelog against core only | Grep each affected subsystem against `custom/` as well. On the 6.7.13.1 upgrade this turned up the single highest-risk item in the whole job — `ATFCatalogImport\Service\MediaImporter` calling `FileSaver::persistFileToMedia()` with an extension derived from the source URL and a `'jpg'` fallback, directly in the path of the new per-write media extension validation. No tool in the pipeline flags it; only reading the changelog and grepping for the touched APIs does |
| Treating a passing plugin test suite as de-risking a specific concern | Check **what the suite covers** before citing it. `MediaImporterTest` passed with 3 tests — all of which exercise skip/failure branches and none of which ever call the at-risk `persistFileToMedia()`. "Tests pass" and "this code path is verified" are different claims; say which one you actually have |
| Reading `plugin:refresh` not discovering an on-disk plugin as the wrong-composer-`type` trap | Check the root `composer.json` `require` list **first**. A plugin dropped from `require` produces an identical signature to the `shopware-plugin` vs `shopware-platform-plugin` trap: present on disk, absent from `plugin:list` even after `plugin:refresh`, and its integration tests failing with `ServiceNotFoundException` because the bundle's `services.xml` is never loaded. `git log -S '<package-name>' -- composer.json` names the removing commit and its intent in one command, separating deliberate test debt from a genuine upgrade regression. When the removal was deliberate (a replacement plugin took over), do **not** re-add the require to green the tests — two plugins owning the same concern can double-apply their effects |
